## Техническая основа

- Проект `WorldGenesis/`. Unity **6000.0.45f1**, C#, 2D сверху, Windows x64. World Genesis — рабочее название, не утверждённое пользователем.
- Редактор: `C:/Program Files/Unity/Hub/Editor/6000.0.45f1/Editor/Unity.exe`. Проверенные пути/статусы — `Tools/toolchain.json`. Наличие файла не доказывает успешный запуск.
- Рабочие решения: Built-in Renderer, ортографическая камера, uGUI, дискретная симуляция. Они обратимы; причины изменений записывать без согласования каждой технической детали.
- Не обновлять Unity/пакеты автоматически. Зависимость добавлять под конкретную задачу, фиксировать версию и импорт. Сохранять `Packages/packages-lock.json`, когда Unity его создаст.
- `Simulation` не зависит от UnityEngine, UI и файловой системы. `Runtime` отображает состояние и передаёт команды. `Editor` не попадает в Player. Границы закреплены `.asmdef`.
- Один владелец состояния мира. UI, VFX, аудио не считают урон, население и экономику отдельно от симуляции. Одинаковые seed, контент и команды должны давать одинаковый результат в проверяемой конфигурации.
- Не создавать GameObject/Update на каждый тайл. Сетка данных, обновление изменённых участков, пространственный индекс. ECS/Jobs/Burst — только по измерениям.

## Метод выполнения

Для реализации действует `Docs/Research/AGENT_QUALITY_STANDARD.md`: сквозной результат, исполнимые проверки, отдельный проход критики и сохранённое состояние. Исследование Anthropic/OpenAI адаптировано к Unity; никаких заявлений «лучше Claude 5.5» без одинакового сравнительного задания. Для сложной системы использовать `Docs/Templates/WORK_PACKET.md` без лишнего документирования мелких исправлений.

1. Выбрать ближайший этап `Docs/ROADMAP.md` и проверяемый результат.
2. Связать изменение с ID функции, критерием и наблюдаемым свойством референса.
3. Реализовать проход: ввод → команда → изменение мира → видимый результат → сохранение, где применимо.
4. Проверить обычный путь, важные границы и прерывания; корректность, внешний вид и производительность отдельно.
5. Сохранить `Evidence/<дата-время>-<сценарий>/`; обновить состояние, критерии и журнал. Повторять проверки при новых изменениях или нерешённых проблемах.

Навыки и пути — `Docs/WORKFLOW.md`. Подключать по задаче. Сейчас применяются production-brief-architect и game-long-run-production. Навыки Godot, кино и 3D-персонажей не являются инструкциями этого Unity-проекта.

Решение пользователя 12.10.2026: использовать субагентов и делегирование, создавать специализированных агентов или привлекать подходящих готовых. Разделять непересекающиеся файлы; один интегратор сцен/редактора/сборки. Роли и фактические инструменты фиксировать в Docs/Development. Это не поручение создавать другие пользовательские чаты, фоновые задачи или расписания.

## Проверки и статусы

Перед процедурной генерацией читать `Docs/Research/IMPLEMENTATION_ROUTE.md` и нужные карточки `Docs/Research/PROCEDURAL_FORMULAS.md`. Различать опубликованный алгоритм, нашу адаптацию и предложенные коэффициенты. Проверять несколько seed, граничные случаи, связность и стоимость; красивый единичный кадр недостаточен. Внешние skills/модули/MCP отобраны в `Docs/Research/TOOLS_AND_AGENTS.md`, но не установлены и не становятся обязательными автоматически.

- Команды — `Tools/README.md`; `Tools/Project.ps1 -Action Validate` проверяет организацию, **не игру**.
- Логика: подходящие EditMode-тесты. Ввод/сцена/UI: PlayMode и Player. Выпуск: настоящая Windows-сборка и обычный запуск.
- Ноль тестов, успешный выход процесса или наличие EXE не означают пройденную игровую приёмку.
- Скриншот — внешний вид; клип — движение; логи/данные — состояние. Обозначать автоматический ввод, debug-помощь, ускорение и offline-рендер.
- Визуальное принятие пользователем отдельно от технического PASS. Концепт не является кадром из игры.
- Неисполненные критерии — `not-run`; ошибки не скрывать понижением требований.
