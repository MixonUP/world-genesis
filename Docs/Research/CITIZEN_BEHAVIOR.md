## Что видно в текущем коде

`SimulationEngine.UpdateUnit/Decide/Work` уже выполняют навигацию, добычу, доставку, производство еды, бой, голод и старение. Сохраняются цели, пути, таймеры и RNG. Проверка склада после разрыва пути существует. Решения разнесены во времени, навигация переиспользует массивы; отдельный framework для этого этапа не нужен.

Приоритеты пока слишком жёсткие: находящийся рядом противник немедленно переключает жителя в бой независимо от истощения и пожара. `Flee` объявлен, но не исполняется. Овцы не убегают от волков. Житель может продолжать работать на горящей клетке. Профессия фактически определяется остатком ID; её нельзя объяснить в инспекторе. Поедание происходит мгновенно во время другого действия, отдельного состояния отдыха нет.

## Рекомендуемый игровой пакет

| Изменение | Наблюдаемое поведение | Последствие в данных |
|---|---|---|
| Реакция на опасность | Работа прерывается при пожаре; овцы бегут от волка; тяжело раненый житель отступает | Новая достижимая цель, освобождение рабочей резервации; урон остаётся реальным |
| Еда отдельным действием | Голодный житель идёт к доступному складу либо еде на местности, останавливается и ест | Однократное списание фактического запаса, уменьшение голода; никакой доставки через пролив |
| Усталость и отдых | После работы/марша житель отдыхает в безопасном месте и возвращается к делу | Накопление/снижение усталости, явные пороги начала и окончания отдыха |
| Понятные профессии | Земледелец предпочитает поля, лесоруб — древесину, страж — патруль и оборону | Профессия изменяет выбор полезной работы; дефицит еды допускает перепрофилирование задачи |
| Короткое общение, если входит в этап | В безопасное свободное время жители ненадолго встречаются у поселения | Потребность в общении снижается только при присутствии живого доступного собеседника |

Первые четыре строки — рекомендуемый обязательный объём. Общение можно включить, если оно не задержит проверяемые угрозу/еду/отдых. Дети не должны вступать в набеги; домашняя жизнь без детального родословного графа достаточна для этого этапа. LLM, GOAP, новые пакеты и тысячи отдельных `MonoBehaviour` не нужны.

## Принцип выбора действий

Это **наша игровая эвристика**. Коэффициенты предстоит подобрать и проверить. Сначала проверяется выполнимость: цель существует, еда доступна, место безопасно, работа имеет реальные входы. Затем сравниваются нормированные потребности с пользой работы, временем пути и небольшим преимуществом текущего действия.

```text
U(a) = need(a) × benefit(a) × roleBias(a) / (1 + travelCost(a))
       + persistenceBonus(a)
```

Действие заменяется при заметном превосходстве новой оценки; экстренная опасность прерывает его немедленно. Возврат из отдыха/бегства требует отдельного безопасного порога, чтобы NPC не переключался каждый тик. Нельзя выдавать эту формулу за оптимальное решение или алгоритм оригинала.

Дорогой поиск пути — после выбора кандидата, с ограниченным числом следующих кандидатов при недоступности. Обычные решения остаются разнесёнными по тикам. Опасность на текущей клетке проверяется сразу; поиск соседних угроз использует существующий пространственный индекс. Путь из горящей области может пройти по повреждающим клеткам, если безопасный выход иначе недостижим; не блокировать бегство требованием уже безопасного первого шага. Плановые маршруты должны избегать известного пожара. Эти случаи требуют отдельных проверок.

## Предложенный контракт Simulation → Runtime

Старые значения перечислений сохраняются. Добавлять только в конец:

```csharp
// Уже существуют: Idle=0, Wander=1, Gather=2, Farm=3,
// Return=4, Fight=5, Flee=6.
UnitTask.Eat = 7;
UnitTask.Rest = 8;
UnitTask.Socialize = 9; // Если общение входит в согласованный объём.
UnitTask.Patrol = 10;

enum UnitProfession { None = 0, Farmer = 1, Forester = 2, Guard = 3 }

// Дополнения UnitData:
public UnitProfession Profession;
public float Fatigue;       // 0 = отдохнувший, 1 = истощённый.
public float SocialNeed;    // 0 = удовлетворена, 1 = велика; при включении общения.
public long TaskStartedTick;

// Дополнение WorldState:
public int BehaviorVersion; // 0 = старые сохранения, 1 = новый контракт.
```

`WorkTimer` уже существует и сохраняется: его можно использовать для длительности поедания/отдыха/общения, не создавая независимый таймер в анимации. `TargetId` обозначает живую цель боя либо общения; очистка при смерти применяется в обоих случаях. Начало задачи фиксируется в `TaskStartedTick`; визуал может связать фазу с игровым тиком и паузой.

Анимационное соответствие: путь ещё не завершён → ходьба, `Flee` → бег, выполнение `Gather/Farm` на месте → работа, `Eat` → еда, `Rest` → отдых, `Fight` с готовым ударом → атака. Направление можно вычислять в Runtime из следующей точки пути/предыдущего положения; оно не обязано становиться игровым полем. Анимация никогда не списывает еду и не наносит урон.

Это рекомендуемый контракт, **не уже существующий API**. Итоговый объём подтверждает интегратор до изменений Runtime.

## Совместимость сохранений v1

`SaveStore` использует envelope/schema 1 и вызывает `WorldState.Validate` до создания движка. Их нельзя ломать обязательными новыми полями, которых нет в старом JSON. Оставить `SchemaVersion = 1`; отсутствующие значения новых полей должны иметь безопасные нулевые значения. Усталость выбрана вместо энергии специально: ноль означает нормальное состояние, а не массовое истощение после загрузки.

Валидатор допускает `BehaviorVersion` 0 и 1 и проверяет новые числа на конечность и диапазон независимо от версии. После успешной проверки конструктор движка выполняет **идемпотентную** миграцию версии 0: назначает профессии через устойчивый hash(seed, id), инициализирует начало задачи, устанавливает версию 1. Миграция не расходует gameplay RNG, не переставляет список жителей и не создаёт ресурсы/сущности. Новые миры используют версию 1 сразу. Для новых жителей поля задаются явно.

Требуется проверить именно загрузку сохранения старой альфы с отсутствующими полями, а не только roundtrip нового формата. Продолжение новой версии обязано быть детерминированным после save/load; совпадение игровой истории с алгоритмом старого бинарника не обещается, поскольку поведение меняется намеренно.

## Приёмка после реализации

- Работа → пожар → бегство → безопасная остановка/возврат; нет телепорта, потерянной ноши и застрявшей резервации.
- Овца увеличивает расстояние до волка по допустимому пути; загнанное животное не проходит воду или стены.
- Высокий голод прерывает необязательную работу; поедание снимает ресурс один раз, доступный склад требует пути/прибытия.
- Истощение приводит к отдыху; отдых уменьшает усталость; пожар прерывает отдых.
- В спокойном городе наблюдаемы разные профессии, реальные циклы добычи/доставки и возврат к работе.
- Загрузка старого v1 без новых полей проходит; миграция повторно не меняет RNG/профессии; повреждённые новые значения отклоняются.
- Save → N тиков и load → N тиков совпадают, включая опасность, незавершённую еду и отдых.
- Нативный профиль 1000 существ сравнивается с предыдущим на одинаковых настройках; новая логика не оправдывает пропуск тиков или уменьшение населения.

Этот список первоначально был планом приёмки. Фактическое исполнение и оставшиеся проверки описаны ниже. Запись в Obsidian выполняет интегратор пакетом проекта.

## Реализация и проверка, дополнение 12.10.2026

Интегратор согласовал весь ограниченный пакет, включая общение. Добавлены `Entities/CitizenBehavior.cs`, расширения модели и навигации; все изменения остаются в чистой C# Simulation. `BehaviorVersion=1` задаётся генератором, значение 0 мигрирует в конструкторе движка после проверки. Случайность миграции — только координатный hash; RNG не сдвигается. Новые задачи имеют именно номера 7–10 из контракта.

Поведение реализовано: поиск достижимого выхода из огня, бегство овец и раненых/детей, предотвращение планового движения в огонь; поедание за 1,2 секунды с однократной транзакцией в конце; отдых до усталости 0,18; роли земледельца/лесоруба/стража с разным выбором работы; патруль; короткий социальный контакт с живым соседом. Ноша переживает прерывание. Переключение с добычи освобождает резерв. Проверка угрозы текущей клетки не ждёт очередного обычного решения. Полный utility-framework не добавлен: приоритет экстренных действий сочетается с нормированными оценками дефицита еды/дерева и профессии.

**Фактическая семантика для анимаций:**

- `TaskStartedTick` меняется только при смене `UnitTask`, сохраняется и не сбрасывается каждым новым маршрутом той же задачи. При миграции равен текущему тику мира.
- `WorkTimer` — оставшиеся секунды действия на месте: 1,2 у еды, 3 у общения. Во время подхода таймер не уменьшается. При переключении задачи обнуляется. У обычной добычи и отдыха он равен нулю; отдых определяется `Fatigue`.
- `PathCursor < Path.Count` означает активный путь. Идущий к полю `Farm` должен отображаться ходьбой; работа начинается по прибытию. `Flee` ускоряет движение. Еда, отдых и общение исполняются на месте.
- `AttackTimer` остаётся сохранённым cooldown удара (0,8 с); реальный урон наносит симуляция. Житель не выполняет действия после смертельного урона текущего тика.
- Потребности `Fatigue`/`SocialNeed` находятся в `[0,1]`; профессия постоянна у взрослого, дети получают её по достижении 16 лет. Новые персонажи имеют небольшое детерминированное разнообразие исходных потребностей.

`Tools/SimulationProbe/Program.cs` расширен с 32 до 38 сценариев. Выполнено **38/38 PASS**, отчёт [citizen-behavior-probe.json](../../Evidence/Simulation/citizen-behavior-probe.json). Проверены прерывание огнём/сохранение ноши, еда/прерывание/ровно одно списание, бегство овцы и отдых, живой собеседник и очистка при смерти, загрузка формы старого JSON без новых полей и идемпотентная миграция, продолжение незавершённой еды/отдыха после save/load. В NUnit добавлены соответствующие случаи; их фактический запуск интегратором ещё предстоит.

Дополнительный текущий сценарий с 12 людьми на плодородной плоской карте: через 1800 тиков — 30 жителей, 24 постройки, положительные запасы еды/дерева. ### Рекомендации следующему этапу экономики — ещё не реализация

Новый запрос о производственных цепочках, животных, караванах и пяти уровнях зданий не включён в завершённый пакет поведения. Чтобы он не разрушил текущие прерывания и сохранения, нужны три раздельных сущности:

1. **Профессия** — постоянная специализация и предпочтения/навыки жителя. Она не должна становиться названием каждой операции рецепта. Голодающий кузнец остаётся кузнецом, пока ест или несёт груз.
2. **Производственное задание** — сохраняемый заказ со стабильным ID, владельцем/зданием, ID рецепта, исполнителем, входами/выходами, зарезервированными ресурсами, достигнутым прогрессом и состоянием. Задание переживает бегство исполнителя; правила остановки и отмены определяют, какие резервы освобождаются.
3. **Текущее действие** — физическое исполнение: идти, забрать, нести, работать, положить, есть, отдыхать, бежать. Вместо нового `UnitTask` на каждый рецепт полезно добавить фазу исполнения и ссылку `JobId`; фактический визуальный action и время его начала принадлежат симуляции. Существующие номера `UnitTask` сохраняются для совместимости до явной миграции.

Склад, производственное здание, груз жителя и караван должны иметь настоящие инвентари. Цикл задания: резерв → фактическое изъятие → перенос → доставка → потребление входов/прогресс → выдача выхода. Транзакции проверяют наличие и вместимость, не дают отрицательных остатков и двойного списания после загрузки. Резерв отличается от наличного запаса. Нельзя одновременно учитывать старый `Settlement.Food/Wood` и новые инвентари как два источника товара.

Рецепты и пять уровней здания лучше хранить в проверяемых definitions: стабильный ID, ингредиенты, выход, длительность, рабочие места, вместимость и стоимость повышения уровня. Экземпляр здания хранит ID definition, уровень/состояние, инвентарь и рабочие слоты. Ограничение рабочих мест исправит нынешнюю модель, где много жителей одновременно производят еду на одной ферме без ограничения мощности.

Караван — транспортное задание с реальным грузом, владельцем, вместимостью, маршрутом и исполнителями/животными; гибель, недоступность маршрута и прерывание не телепортируют товар. Дикие животные используют общие движение/опасности/потребности, но отдельные видовые цели, размножение и питание без профессии и гражданских производственных заказов.

Первый сквозной вертикальный срез: дерево → лесопилка → доски → реальное улучшение дома с уровня 1 до 2; затем зерно/переработка/еда, металл, остальные уровни и перевозка между поселениями. Проверять сохранение массы товаров, слоты рабочих, недоступные входы, голод/пожар во время перевозки, отмену/смерть, save/load на каждой фазе. Для структурной смены инвентарей нужна явная версия экономики/миграция, сохранённый fixture прежнего JSON и защита от повторного переноса запасов. Значения производительности, рецепты и баланс не объявлять уже реализованными по одной таблице.

## Уточнение пользователя: гражданское основание и временное ополчение, 12.10.2026

Реализован новый обязательный порядок: основание поселения, дополнительный спавн и взросление назначают только земледельца или лесоруба. Никаких профессиональных воинов/рыцарей без исследования и фактического снаряжения. Эти две системы пока отсутствуют, поэтому военный найм недоступен полностью; фиктивные флаги «исследовано»/«экипирован» не добавлены.

`UnitProfession.Guard=3` и `UnitTask.Patrol=10` оставлены в перечислениях ради совместимости, но их автоматический выбор удалён. Номер потока hash гражданских профессий сохранён; прежние земледельцы/лесорубы не меняют распределение, бывший случайный слот стража становится земледельцем. Профессиональные марши к центру вражеского города, патрули и повреждение зданий гражданской задачей Fight удалены.

**Временное ополчение:** взрослый дееспособный гражданский при локальном противнике получает `UnitTask.Fight`, сохраняя `Profession`, потребности и ношу. В коде угроза — ближайший враждебный житель или волк в окрестности ±2 клеток; отдельная история объявления мобилизации/политических приказов не выдумывается. Это реакция на близкую угрозу, не поход из-за одного `EnemyId`. Урон и cooldown удара принадлежат симуляции. Когда враг погибает или выходит из локального восприятия, житель возвращается через обычный выбор к гражданскому действию. UI может показывать «Ополчение: защита» для цивилизованного `Fight`, не переименовывая профессию в стража и не дорисовывая бесплатную броню. Дети младше 16 лет и жители с HP ниже 35% максимума выбирают `Flee`; огонь также имеет приоритет перед боем.

### Миграция BehaviorVersion 2

Генератор создаёт версию 2. Сохранения версии 0 и экспериментальной версии 1 сначала проходят валидацию, затем конструктор движка мигрирует их один раз:

- Для 0 по-прежнему инициализируются отсутствовавшие потребности/профессии; теперь только гражданские.
- В версии 1 неподтверждённые `Guard` получают гражданскую профессию через устойчивый hash. Их приказы `Patrol`/`Fight` отменяются: задачи становятся Idle, цель и маршрут очищаются, новое решение готово на следующем тике.
- Потребности и обычные действия остальных жителей версии 1 сохраняются. Ноша, население, ID, часы мира, RNG и склад не расходуются. Повторное создание движка не повторяет миграцию.
- В текущей версии 2 валидатор отклоняет `Guard`: в модели ещё нет данных, которые могли бы подтвердить такой найм. Старые версии допускают это значение только для безопасной демобилизации. Enum IDs и `SchemaVersion=1` не изменены.
