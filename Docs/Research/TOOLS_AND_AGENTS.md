Даже официальные инструкции требуют привязки к задаче. Pixel-perfect skill различает Built-in и URP — это полезно. Его рекомендации о разрешении и частоте physics не являются измеренными требованиями нашего симулятора. В ui-ugui фраза «working UI» трактуется как корректная видимая иерархия; в нашем задании UI должен выполнять команды мира, поэтому явно задаём обработчики, блокировку клика сквозь панели и PlayMode-проверку.

BMAD полезен как редактор проектных документов; его README прямо отделяет дизайн от полной реализации игры и производства арта/музыки. Ни один изученный framework не заменяет работающую симуляцию, её профилирование и игровую проверку.

## Как назначать работу агенту

Оставляем один канонический набор инструкций: корневой AGENTS → STATE → документ текущей системы. Роли «дизайнер», «архитектор», «программист», «ревьюер» — последовательные режимы работы, не поручение запускать подагентов.

Для каждого изменения передавать:

1. Наблюдаемое поведение игрока и ID приёмки.
2. Владелец состояния и границы изменяемых файлов.
3. Входы/выходы алгоритма, единицы, порядок вычислений и RNG.
4. Источник метода и отличие нашей адаптации.
5. Один нормальный сценарий, существенный граничный случай и способ воспроизведения.
6. Ожидаемый артефакт: код, журнал Unity, данные, кадр/клип; статус того, что ещё не запускалось.

Новые внешние skills сначала читать как исследуемый материал. Не переносить оттуда автоматически установки, миграции рендера, глобальные настройки, платные сервисы или дополнительные процессы. Выбранные инструкции должны дополнять пользовательский запрос, а не менять его объём.

Не путать аргументы Unity.exe -batchmode из Tools/Project.ps1 с отдельным новым продуктом Unity CLI. Уже подготовленные команды остаются действующими инструкциями проекта; новый CLI ещё не обнаружен/проверен локально в рамках этого исследования.

Конкретная несовместимость функций: документация Pipeline 0.5 относит capture UI Toolkit element к Unity 6000.7+. Это не основание переносить такое требование на все остальные команды или автоматически обновлять наш редактор.

Поиск «Unity» в доступном каталоге плагинов не вернул подходящей карточки. Это результат данного поиска, а не утверждение об отсутствии Unity-интеграций вообще. Установки по веб-ссылкам не выполнялись.

Проверка выбранного моста после успешного запуска редактора: установить точную версию → прочитать версию и активную сцену → создать/удалить собственный временный тестовый объект → проверить компиляцию и непустой тестовый запуск → захватить Game View → убедиться, что Player не содержит зависимость от сервера. Фиксировать журнал, настройки и способ отключения. Несколько серверов, изменяющих один редактор, не нужны.

## Минимальный стек по результатам исследования

Сейчас: существующий каркас + встроенные Unity Tilemap/uGUI/Test Framework + собственная C# модель мира + выбранные алгоритмы. При первом рельефе — оценить закреплённую C#-версию FastNoise Lite. При работе в редакторе — официальный Unity Agent Plugin как кандидат инструкций; для доступа к редактору выбрать один из M01/M02 после проверки. WFC, GOAP, сторонний pathfinding и DOTS остаются решениями конкретных последующих задач.

Установленное, подготовленное и рекомендованное вести раздельно. Ни один внешний компонент в этой таблице не получил статус «проверен в нашем Unity-проекте».
