# Инструкции для сильного результата агента в Unity

Дата: 12.10.2026. Дополнительное поручение пользователя: найти инструкции, позволяющие делать игру не хуже Claude 5.5, а лучше. Цель этого документа — повысить качество реализации и сделать сравнение проверяемым. Превосходство какой-либо модели не установлено; сравнительный запуск не проводился.

Ни один источник не доказывает, что длинный системный промпт, больше ролей или бесконечный цикл обеспечат превосходство над сильной моделью. Практически полезны качество задания, доступ к рабочему редактору, объективная обратная связь и исправление обнаруженных дефектов. Ниже — наша адаптация этих принципов к данному проекту.

## Рабочий стандарт

1. **Сохранять полную цель.** FEATURE_MAP и ACCEPTANCE определяют объём. Первый остров с юнитом не означает завершённый аналог WorldBox. Не удалять трудную функцию и не снижать критерий ради зелёного статуса.
2. **Начинать с фактов текущей ревизии.** Прочитать STATE, проверить существующие файлы и последнее доказательство. Известный сбой запуска сначала диагностировать. Не складывать новые непроверенные системы поверх неисправной основы.
3. **Один шаг — видимое поведение.** Формулировать «игрок рисует землю, путь жителя перестраивается», а не «созданы 12 менеджеров». Для исследования результатом служат проверенный метод и запись его ограничений; реализацией он становится после интеграции.
4. **Для сложной системы — короткий исполняемый план.** Использовать [шаблон рабочего пакета](../Templates/WORK_PACKET.md). В нём должны быть владелец данных, контракт, риск, проверка и следующее действие. Для простого исправления не плодить документы.
5. **Сначала подтвердить риск.** Для стока — плато/впадина; для save — roundtrip и испорченный файл; для UI — реальный ввод; для массовых существ — профиль. Эксперимент ограничен конкретным вопросом и выводом, после него продолжать реализацию.
6. **Закончить сквозной путь.** Ввод → команда → данные → изображение/звук → сохранение, где применимо. Заглушка, демонстрационное число населения, неработающая кнопка и нарисованный эффект без игрового воздействия не закрывают функцию.
7. **Проверять на правильном уровне.** Чистую модель — EditMode; компоненты и ввод — PlayMode; пользовательский маршрут — Player. После подтверждённых достаточных проверок переходить дальше; не запускать одинаковые проверки ради количества.
8. **Исправлять причину.** Сначала воспроизведение и наблюдение, затем гипотеза и узкое изменение. Не глушить исключение, не отключать упавший тест и не добавлять случайный fallback, чтобы скрыть проблему. Ошибочный тест можно исправить с объяснением первоначальной ошибки.
9. **Делать отдельный проход критики.** После реализации оценить результат по исходному заданию: какие данные могли стать неверными, какой путь игрока не пройден, какой дефект видно при обычном zoom. Саморевью обозначать как саморевью; независимой экспертизой оно не становится.
10. **Проверять художественное качество предметно.** Сопоставлять реальные кадры с референсом: масштаб тайлов/юнитов, читаемость берегов и биомов, силуэт поселений, палитра, порядок слоёв, дрожание при pan/zoom, обратная связь кисти, плотность HUD. Для движения нужен клип. Слова «красиво» или «похоже» без наблюдаемого признака недостаточны.
11. **Измерять стоимость.** Записывать размер мира, население, скорость времени, железо, CPU/GC/memory и p95. Не оптимизировать по авторитету чужого benchmark и не подменять реальное FPS скоростью offline-рендера.
12. **Оставлять возможность продолжить.** STATE содержит последний работающий сценарий, проверенную ревизию/хеши, открытые дефекты, активные процессы своего задания и следующий конкретный шаг. Технические решения — в DECISIONS, большие логи — в Evidence. Не перечитывать весь архив на каждом шаге.
13. **Действовать без лишней передачи работы пользователю.** Внутри порученного объёма самостоятельно исправлять обратимые проблемы и продолжать следующий подготовленный шаг. Спрашивать лишь при существенном недостающем решении/разрешении; уже данное разрешение не запрашивать заново. Отсутствие ответа не считается согласием на действие, которому оно необходимо.
14. **Закрывать пункт по доказательству.** Успешная компиляция не равна работающей игре. Приложить команду, ненулевой набор выполненных сценариев, фактический результат, путь к evidence и ограничения. Непроверенное остаётся not-run; плохой вид не становится принятым из-за технического PASS.

Этот стандарт не запускает подагентов, hooks, расписания, платные запросы или смену модели. Подходы Q01–Q03 с отдельными агентами сейчас адаптированы как последовательные этапы работы. Если независимый ревьюер будет отдельно поручен, ему нужны исходные критерии и реальные артефакты, а не только самоотчёт автора.

## Как сравнивать с Claude 5.5 на деле

Сравнивать результаты одинакового задания, а не количество файлов, длину ответа или самопроставленные оценки. Условия фиксируются до запуска: точная модель и среда, исходная ревизия, Unity/пакеты, доступные инструменты и ресурсы, время/стоимость, степень ручной помощи. Текущий Claude-сравнительный образец отсутствует.

| Сценарий | Что измерить | Связь с приёмкой |
|---|---|---|
| B01 · Карта и кисть | Детерминизм, края карты, pan/zoom, корректное попадание, отсутствие клика сквозь UI | A02, A06, A10 |
| B02 · Реки и ресурсы | Сток без циклов, баланс, соблюдение обещаний пресета на наборе seed | A13 |
| B03 · Поселение | Реальные задачи/расходы/строительство, реакция на голод и разрыв пути | A03 |
| B04 · Силы | Огонь/дождь/урон изменяют состояние; визуальная обратная связь соответствует данным | A04 |
| B05 · Save/load | Продолжение тех же команд даёт тот же результат; повреждённый save безопасно отклонён | A05 |
| B06 · Вид и управление | Слепое сравнение равноценных native кадров/клипов без названия модели; предпочтение пользователя и список дефектов | A06, A07 |
| B07 · Нагрузка | p95 кадра, память, GC, ошибки при одинаковом мире/ПК | A11, A12 |
| B08 · Продолжение | После восстановления контекста сохраняются объём, рабочий сценарий и следующий шаг; нет повторной переписи готового | STATE + повтор сценария |

Сначала жёсткие отказы: не запускается, теряет сохранение, не выполняет главную механику. Затем сравнивать полноту поведения, дефекты, внешний вид, производительность и затраты по отдельности. Красивый кадр не компенсирует потерю мира; больше функций не доказывает лучшую графику.

Для содержательного вывода потребуется несколько одинаково подготовленных попыток; число и бюджет назначить перед реальным сравнением. Не выдавать случайный удачный запуск за общее превосходство. Если доступен только один проект, результат — оценка по требованиям, без утверждения о победе над Claude.

## Короткая инструкция исполнителю

«Доведи выбранный этап World Genesis до наблюдаемого результата в Unity. Сохрани полный объём FEATURE_MAP и закреплённую архитектуру. Начни с STATE и последнего evidence, выбери один незакрытый сквозной сценарий. Реализуй его, запусти соответствующие проверки и исправь обнаруженные причины отказа. Затем выполни отдельный проход критики функциональности и настоящего вида при игровом масштабе. Не закрывай критерии заглушками, самооценкой или компиляцией без поведения. Продолжай порученную работу без лишних запросов подтверждения. Обнови STATE/ACCEPTANCE/Obsidian фактами и оставь воспроизводимое доказательство. Если сравнения с другой моделью не было, не заявляй превосходство».
